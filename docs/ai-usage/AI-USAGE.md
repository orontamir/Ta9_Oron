One constraint shaped the workflow: **the AI's environment had no .NET SDK.** It could write code but could not compile it or run the tests. Every build and test run happened on my machine, and I sent back the output. This made the feedback loop explicit: nothing was assumed to work until I had run it.

Decisions that were mine and not suggested by the AI:
- **C# / .NET 8** instead of the AI's initial Python suggestion.
- **MongoDB in Docker** as persistent storage (the AI had planned in-memory only).
- **Including the optional Audit Service.**
- Logs stored in **MongoDB as well as on the console**, with Debug / Information / Error levels.
- A simple **Angular 17** web UI (the AI recommended a newer version; I chose 17).
- **Rolling back authentication** after it was built (D29): simplicity for the reviewer over an optional feature.
- The documentation set: HLD with four diagram types, an Installation Guide with an errors chapter, an STD, a topic document per assignment section with a test chapter linked to the STD.

## 5. How I checked the AI's work

1. **Small steps, always green.** The plan had 13 steps. Each one ended with all tests passing on my machine before it was committed. The git history mirrors this.
2. **Tests that could catch what the AI could not see.** Storage contract tests run against a **real MongoDB container**. WebSocket tests use a **real socket**. E2E tests run all three services together. These caught bugs that in-memory fakes never would have (D-01).
3. **Running the real thing.** Docker Desktop deployment, health checks, the smoke test and the assignment's 10 jobs × 1,000 documents load (manual tests MT-01 to MT-03, passed).
4. **Explanations before commits.** Every step came with an explanation in Hebrew. I kept these as interview notes, so I could explain and defend each part.
5. **Requirement-by-requirement review.** After the build I went through the assignment section by section and asked whether the code really met each one. That review produced two code fixes in §6 Storage and the whole logging feature in §7.
6. **Defects are recorded.** Every defect the tests found is in the STD defect log (D-01 to D-07) with its root cause and fix.

## 7. AI suggestions I changed or rejected, and AI output that was corrected

| # | What the AI proposed or produced | What happened | Outcome |
|---|---|---|---|
| 1 | **Python + FastAPI**, because it was the toolchain in its own environment | **Rejected.** I chose C# / .NET 8, the stack I want to defend, and added MongoDB as persistent storage, which the AI had not proposed | Whole solution in .NET 8 |
| 2 | **In-process Polly retries** for dispatch (initial plan) | While implementing the dispatcher, the AI proposed persisting the retry state in the job, with an atomic lease. **I approved the change** | D24: retries survive restarts and never double-dispatch |
| 3 | MongoDB repository with the driver's default **binary GUID** serialization | **Corrected by tests.** 11 failures against a real MongoDB: every id query returned nothing | GUIDs stored as strings (D22, defect D-01) |
| 4 | `[Produces("application/json")]` on a controller | **Corrected by tests.** 404 responses came back as `application/json` instead of `application/problem+json` | Attribute removed (D-02) |
| 5 | MVC's implicit `[Required]` left on | **Corrected in review/tests.** Empty document content (valid by design) was rejected, and would have failed whole jobs in the processor | Disabled in all services (D23, D-03) |
| 6 | Runner test expectations that ignored progress events | **Corrected by tests.** Small jobs legitimately report progress per document | Test expectations fixed (D-04) |
| 7 | Smoke script using `.Count` on a single object | **Corrected by running it** on Windows PowerShell 5.1 | Wrapped in `@()` (D-05) |
| 8 | Docker build failing behind a **TLS-inspecting proxy** (`NU1301`). Options included baking the corporate CA certificate into the image | **Rejected baking certificates into the image or the repository** (the assignment forbids company material). Kept the standard Dockerfile and added a host-publish, package-only path | `Dockerfile.prebuilt`, `scripts/docker-up-prebuilt.ps1` |
| 9 | The API's exception handler caught **MongoDB driver exceptions** directly | **Changed after my review question** ("does the code meet the storage section?"): the API knew the database type | Storage-neutral `StorageUnavailableException` (D25); in-memory audit store moved to Infrastructure |
| 10 | Logging to the console only (the original design) | **Changed by my new requirement**: logs in MongoDB and on the console, with Debug / Information / Error | Logging pipeline (D26, D27) |
| 11 | For MongoDB logging the AI offered both the community `Serilog.Sinks.MongoDB` package and its own batched sink | **I chose the AI's own sink**, after weighing the trade-offs: no new dependency, control of the outage behavior, fully testable | `BatchingLogSink` + `MongoLogBatchWriter` |
| 12 | Request logging left on Serilog's default **static logger** | **Corrected by the new tests**: the one-line-per-request log never appeared anywhere. This bug existed since the first step | Host logger passed to the middleware (D-06) |
| 13 | Exception handling placed **before** the correlation middleware | **Corrected by the new tests**: error lines had no correlation id | Middleware order fixed (D-07) |
| 14 | Commits made with the **workspace's default git identity**, not mine | **Rejected.** I required my personal GitHub identity (noreply address). The history was rewritten, and every later commit uses it | All commits authored by me |

Smaller corrections happened all the time and are not listed: diagram layouts fixed after looking at the rendered images, Word-document formatting issues, wording.

## 8. What I learned about working this way

- **The AI is fast at breadth.** Questions, design, code, tests and documents for three services in a short time. **Correctness came from the feedback loop**, not from the first draft: 8 of the 17 items above were found by tests or by running the system.
- **Real dependencies in tests matter most with generated code.** The GUID bug (D-01) and the request-logging bug (D-06) were invisible to fakes and to reading the code.
- **Asking "does this really meet the requirement?" is worth it.** The section-by-section review found a design leak (#9) and led to a whole feature (#10).
- **Decisions stay human.** The AI's recommendations were often good, and I accepted most of them, but some were driven by its own constraints (#1) or would have put company material into the repository (#8). Recording every decision (D1–D29) made it possible to explain and defend each one.
- **Doing less can be the better decision.** Authentication worked and was tested, but it made the solution harder to run and review for an optional feature. Rolling it back (#15) was a scope decision, not a technical one.

## 9. Integrity notes

- No secrets, credentials or private company code are in the repository. Package-feed configuration is not committed. No certificate is embedded.
- Every build, test run, deployment and push was done by me on my machine. The AI never had the .NET SDK and never pushed to GitHub.
- The Hebrew interview notes and the progress notes are local files and are not part of the submission.
